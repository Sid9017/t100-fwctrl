# 小程序线上服务接入记录

## 菜品图像分析（直连 skcale-server）

2026-10-15：小程序已接入真实请求路径，API origin 为 `https://skcale-api.haivivi.cn`，不经过 Netlify。新增服务端需求仅为微信登录，跟踪 [skcale-server #1](https://github.com/h2vivi/skcale-server/issues/1)。此前建议新增结果 GET 接口已撤回，结果复用现有 PowerSync。已交叉核对服务端最新提交 `ca18175` 和 [PR #2](https://github.com/h2vivi/skcale-server/pull/2) 的请求/响应契约；PR 提交不代表线上已部署。

### 请求与凭证

1. `wx.login()` 获取临时 code，发送到拟新增的 `POST /api/v1/auth/@loginWechat`。AppSecret 仅由服务器保存。
2. 复用现有 accessToken/refreshToken 会话；业务 REST 使用 Bearer，PowerSync 使用现有 Token 鉴权。当前用户的本地餐次与云端 ID 单独映射。刷新令牌失效时单次静默重新登录，微信 code 失效时只换取一个新 code 重试；配置缺失、上游不可用及禁用用户分别反馈。重新登录后身份变化则停止原用户的数据写入与同步读取。
3. `files/@signUpload` → 预签名 PUT → `files/@commit`，上传不附带业务 Bearer。按图片字节识别格式，不依赖本地文件后缀；未登记成功的文件不提交餐次。
4. 创建餐次时发送稳定 `Idempotency-Key`，再调用 `POST /intake-records/:id/@analysis`。
5. 从现有 `POST /powersync/sync/stream` 读取 `intake_records`、`intake_photos`。适配层处理 NDJSON 分块、UTF-8、checkpoint、校验和、64 位操作 ID、重连与任务 ID 匹配，不依赖新增 GET。

小程序后台须配置 API 及实际预签名上传域名为合法 request 域名，保持域名校验开启。微信登录接口尚未部署；未完成真实用户登录、上传和分析闭环联调。已有测试使用模拟传输，不能视为线上分析成功。

### 返回值与页面

- `miniprogram/utils/skcale.js` 负责会话、上传、餐次及分析请求；`src/miniprogram/powersync.js` 负责同步读取；`miniprogram/utils/food-analysis.js` 映射 UI 数据。
- 返回整份热量与碳水、蛋白质、脂肪、膳食纤维。按服务端整份结果显示，不在本地随称量重新推算。缺失营养字段保留 null，不能补填或自动记录为 0。更改重量后重新计算；新结果替换旧版手动覆盖。
- 每道菜以 Ingredients 展示 `items` 的食材名称与克数，兼容旧缓存将食材拼接在 description 的记录，整餐展示 `suggestion`。服务端目前没有单独的菜品分析段落字段。完整餐次重算更新整餐建议。修正食材/描述通过 `POST /intake-records/:id/@edit` 提交最多 200 字文字及全量保留组的 photoId，再按 jobId 读取新结果。已有餐后照片一并保留，避免全量提交误删。
- 拍照先在转盘页底部拉起按内容自适应高度的称重面板，仅记录照片、净重和容器；关闭时向下收起并自动保存草稿，不触发分析。转盘页通过拖动照片后快速顺/逆时针甩动，或长按中心相机，最多五张图一次提交到同一个餐次，调用一次 @analysis，随后通过 PowerSync 获取每道菜的热量、四项营养、食材描述及整餐建议。图片的签名上传/登记、餐次创建或更新仍是独立网络步骤，不是把整个上传流程压成一次 HTTP。
- 计算期间转盘保持甩动方向，线性变速至匀速旋转；中心圆形先收缩并淡出相机，再展开并淡入心跳；餐类标题右侧显示加粗的 Analyzing…，并锁住拍照/删除/切换餐类；完成或失败后从当前角度沿原方向线性减速，在 2.4 秒内恢复原速；通过单个角度时钟连续更新转盘与照片的反向旋转，避免长原生动画残留、叠加或回到初始角度。整批结果校验通过后一次写入本地，显示当前选中菜品结果（营养默认折叠）和整餐建议。增删照片或修改净重后清除旧整餐建议，可再次甩动或长按中心相机；改重的菜品营养保持未知直到重算，不在本地伪造零值。退出、删除、输入改变或账号切换后的迟到响应不会回填。分析受理回执丢失时保留待处理任务，重试复用其结果而非重复计费。
- 完成后保存结果，重新打开复用缓存；旧 mock 缓存不能当作真实服务结果。只有隔离的 `preview` 场景返回明确标记的示例数据，正式流程失败不会降级为 mock。

### 联调边界

本次是分析请求和结果读取，并非完整云端双向编辑同步。直接营养覆盖已移除。菜品/餐次删除及本地容器 UUID 的云端同步尚未接入（服务端已有删除/容器 CRUD 接口）；本地删除不会自动撤销已提交的云端分析。固件离线队列与云端同步是不同通路。

## 餐次详情编辑与同步

- 餐次详情选中照片后淡入共用的热量和营养素表；不提供评分编辑、Send to device 或 Done。称重修改立即保存，显式提交整餐计算后更新服务端结果。
- 转盘甩动/长按调用上述整餐适配器；只有隔离预览使用 mock，也一次返回所有照片的结果。食材纠正通过选中菜品下的 Apply correction 发起 @edit，并原子更新整餐返回值。失败保留原值并恢复按钮，错误显示于转盘下方。
- 餐次 UUID 和原始时间保持不变。本地记录按设备保存待同步状态；连接且认证完成后，先同步单位/目标，再处理删除与餐次更新。发送期间出现新修改时，不用旧请求的完成状态确认新数据。
- 固件现有 `appendKcalHist` 接口接收 UUID、时间、总热量、评分和最多前三张照片；完整五张照片及营养素保留在小程序。离线或断线时保留待处理记录，重连/回到前台重试，前台失败每分钟重试一次。当前通过模拟传输测试，尚未真机验证固件按相同 UUID 更新的结果。

## 资料与营养计划（2026-10-15）

- 资料表单使用真实生日，不从旧 age 猜生日；目标周期改为 paceKgPerWeek。客户端校验与现有服务端一致：身高整数 60–250 cm、体重 20–300 kg、体脂 3–36%、目标体重变化不超过当前体重 15%、减重 0.1–1.0 kg/周、增重 0.1–0.5 kg/周。维持体重不发送目标体重/速度。
- 第三步明确「Save and calculate」，通过 `PATCH /users/profile` 保存身体/目标输入并重置 targetKcal 为 null，使用响应中的 plan 显示 TDEE 和营养目标。第四步只 PATCH targetKcal、carbPct/proteinPct/fatPct、fiberG，不重发身体字段或新增体重日志。目标 100–9999，比例整数且合计100，纤维25–140。TDEE不可手填；未公开性别由服务端公式处理。
- 启动/回前台经同一 Token 协议订阅 users、user_profiles、user_plans。按完整且校验通过的 checkpoint 恢复 birthday/gender、档案与服务端计划，主键使用内部 user.id，后两表在同步流中 user_id AS id。网络错误/不完整 checkpoint 与确实缺少档案区分；恢复未完成时不显示可提交的建档表单。成功写接口的响应立即落本地，迟到的旧快照不得覆盖新写入。
- 正式 journal 改为 `kcalack.journal.v1:<user.id>`，草稿同样按 user.id 隔离；切换用户立即切换内存与缓存，迟到请求不得跨用户保存。旧无归属的 v1 缓存保留在原键，不自动认领或上传到当前微信用户。固件同步在用户切换时终止旧批次。历史餐次、容器的云端全量恢复不在本次 profile/plan 快照范围。
- 容器新建/编辑要求照片，名称最长64字、最多50个、重量不超过1999 g，UUID仍为本地/固件标识，不能直接当服务端 containerId。旧无照片容器仍能展示，重新保存时需补图。
- 不提供微信账号注销流程。固件历史协议保留既有 rating 字段及兼容默认值，但不向用户展示可编辑评分，也不将它伪称为服务端评分。
- 自动化测试验证接口契约、账号隔离、完整快照、离线错误、写入/同步竞态、@edit 与任务回执恢复。均为本地模拟传输，真实登录、PowerSync 和部署仍须线上联调。

## 转盘交互（2026-10-15）

- 删除 Calculate meal 独立按钮。照片可跟手顺/逆时针旋转；最近 120 ms 的角速度达到 210°/s、累计转动至少 22° 才触发，松手前停住超过 140 ms 不触发。多指、取消、穿过圆心不会提交；甩动后的 tap 不会误打开菜品编辑。长按中心相机是替代入口。
- 松手后保持方向，以固定加速度在 800 ms 内过渡到 180°/s，结果成功或失败后用 2400 ms 线性降速到 7.5°/s。角度按真实时间积分，以 32 ms 单时钟更新视图并做线性插值；照片使用相反角度保持正立，不叠加两个独立旋转动画。后台暂停，返回时从原角度恢复。
- 中心相机与心跳以“收缩淡出 → 换图标 → 展开淡入”双向切换；按住照片时在餐类标题同一行右侧显示加粗的 Drag fast to analyze，分析完成后提示淡出。提示节点保持挂载，灰绿色拖动提示与灰蓝色分析提示通过淡出、淡入切换。转盘下方不显示常驻或计算阶段提示。五张照片上限只禁用拍照，不禁用长按分析。
- 服务端当前公开字段为每道菜 foodName/items 和整餐 suggestion，没有独立菜品 description。仅呈现 Ingredients，不显示单个菜品 description，不能把整餐建议复制成每道菜描述，也不能伪造缺失内容。

- Food journal 的餐次入口复用转盘及分析结果编辑界面。通过餐次 ID 打开时固定餐类和时间，不允许切换餐段；使用对应餐类的静态山坡太阳背景。
